# Socket reconnects and Health-log gaps: what the documentation says

Read 2026-11-06. Primary sources only; anything else is marked UNVERIFIED. The period of the user's "closed, reopening" errors is NOT established here; nothing below assumes one.

## 1. What our code does (file:line)

All paths under `src/js/`. "Worker" = `collectors-worker.js` unless stated.

### Common mechanics
- `say(name, err)` (worker:17-20) posts a `collector error` note at most once per source name per 5 minutes (`said[name]`, 300000 ms). So a source that closes every few seconds shows as one "closed, reopening" line per 5 minutes, not one per close. The page turns notes into Health-log entries at `collectors.js:66` (`hlNote(m.k, m.d)`).
- Every socket's `onclose` handler says `"closed, reopening"` and reopens after a fixed 5000 ms (no backoff, no jitter, no cap, no retry counter). Lines: stream 70, wallets 87, options 130, venues 166, trades 192, perp book 230, perpFlow 265, Binance book 314, HL book 326.
- `onerror` is not handled in any worker socket, and the close `code` / `wasClean` / `reason` is never read or stored. The Health log therefore cannot tell 1006 from 1001 from a server close code (for example Deribit 4000).
- The worker has one 1 s `setInterval(tick)` (worker:399); the silence checks below run inside it.
- A silence check closes the socket itself (`w.close()`), which then runs `onclose` and prints "closed, reopening". So a quiet-but-alive socket produces the same message as a server drop. The message does not say which happened.

Observations that follow from the table (facts about our code, not about causes):
- Several silence thresholds are shorter than what a venue documents as its own idle limit (see section 2): 15 s for Binance derivs, 30 s for venues, books, HL. Whether a legitimately quiet channel exists below those thresholds depends on the instrument; the code assumes there is none. A 1 s markPrice stream and a busy BTC trade channel will not go 30 s without a message, but Coinbase `ticker`/`matches` and Hyperliquid `userFills`-only periods were not checked.
- The `userFills` subscriptions on the wallets socket count against Hyperliquid's "10 unique users" limit (section 2); we follow `COLLECT.WALLET_TOP` wallets (rotating, with unsubscribe of dropped ones, worker:94-95).
- Each recording can hold, per tab, one HL socket each for wallets, book and tradeVol plus the page feed: about 4 HL connections per open page, against a documented per-IP cap of 10.

### Health log (`health-log.js`)
- Heartbeat: a 1 s `setInterval` on the PAGE thread (line 48-71). If the wall-clock delta since the last tick is over 4000 ms it writes a `gap` note with `gapMs`, `monoMs` (performance.now delta), `vis`, `focus` and `why` (line 50). `why` = "clock jumped (the computer slept?)" when wall minus monotonic exceeds 3000 ms, else "timers delayed (tab throttled or frozen)". Note: `performance.now()` may not advance across a system sleep on every platform, so the classification is a heuristic (UNVERIFIED for Chrome on Windows).
- So a "gap" note on every minute means the PAGE timer was firing about once a minute, not that a socket dropped. The collectors' Worker is separate (see section 3).
- Other notes: `silent` / `back` when `sbSnapshot().venues[bn|hl].ageMs` exceeds 10 s on the page feeds (lines 53-57); `price-stream drop` from the auto-record worker (line 61); `wake lock lost` (62); `tab hidden/visible` (73); `page frozen by the browser` on the `freeze` event and `page resumed` on `resume` (74-75); `pagehide` (76); `load` with `discarded: document.wasDiscarded` (43).
- What the log does NOT record: any socket's close code, `wasClean`, time connected, or time since last message for the worker sockets (only the text "closed, reopening" and an error string). Only the auto-record stream records `upMs` and `silentMs` (auto-record-worker:15).

## 3. Browser behaviour for a hidden page and its Worker

1. Timers in a hidden page (Chrome's own documentation):
   - Chrome 88 timer article (developer.chrome.com/blog/timer-throttling-in-chrome-88): a page that is hidden is "throttled" to roughly one wake-up per second; after being hidden for more than 5 minutes, with a chain count of 5 or more (a `setInterval` counts, each iteration adds to the chain), no sound in the last 30 s and no WebRTC, it becomes "intensive" throttled: roughly one wake-up per minute. Silent audio does not exempt. An open WebRTC data channel or live media track does. The article does NOT list WebSocket as an exemption, and does not discuss Web Workers.
   - Background-tab article (developer.chrome.com/blog/background_tabs): budget-based throttling starts 10 s after the page is hidden, budget regenerates at 0.01 s per second. Pages with WebSocket or WebRTC are exempt from the BUDGET rule ("so the connections aren't closed by timeout") but the once-per-second rule still applies to them. That article is old (about Chrome 57); whether it still describes current behaviour is not confirmed by a newer first-party page I could read.
   - Consequence consistent with the Health log: our page heartbeat (`setInterval` 1 s) is exactly the kind of chained timer that is slowed to about once a minute in a long-hidden tab. A `gap` note about every minute is the documented intensive-throttling signature for PAGE timers. This tells nothing about the Worker.
2. Timers and sockets in a dedicated Worker created by a hidden page: the Chrome pages I read do not say whether worker timers are throttled, exempt, or frozen along with the page. The Page Lifecycle article does not say what happens to Web Workers when the page is frozen; it only recommends moving non-UI work to a worker. The comment at worker:2 ("its timers and sockets are not slowed with a hidden tab") is the app's own observation, not a documented guarantee. UNVERIFIED from primary sources.
3. Frozen and discarded pages (developer.chrome.com/docs/web-platform/page-lifecycle-api, "Overview of Page Lifecycle states and events"; "Developer recommendations for each state"): when a page is frozen, freezable tasks in its queues, including timers and fetch callbacks, do not run. When discarded, no code runs and no events fire; check `document.wasDiscarded` at load. For the Frozen state the recommendation is to release held Web Locks and to stop polling or close open WebSocket connections, and to reopen them on resume. The article gives no full list of conditions that prevent freezing; it points to a separate Chrome heuristics document that I could not read. So whether an open WebSocket or a held Web Lock prevents freezing is not established by what I read.
4. Memory Saver (support.google.com/chrome/answer/12929150, first-party Chrome help): inactive tabs are deactivated (reloaded when opened). Listed exceptions: active audio/video including calls, screen sharing, notifications, downloads, partially filled forms, pinned tabs, connected USB/Bluetooth devices, and the user's "Always keep these sites active" list. A WebSocket, a Web Lock and a wake lock are not on that list. Note: our `overnight-view.js:28` already warns about Memory Saver.
5. Web Locks (w3.org/TR/web-locks, section 2.6 "Termination of Locks"): when a document unloads, or an agent terminates, its held locks are terminated. The spec is silent on frozen, bfcache or discarded states, and says there is "no normative way to run steps on worker termination". Workers sharing a storage bucket share the lock manager. Holding `sv-armed` is therefore a statement about the page's existence, not a documented exemption from freezing or throttling.
6. Screen wake lock (w3.org/TR/screen-wake-lock, section 11.3, and 8.1): when the document's visibility becomes hidden the user agent releases every active screen wake lock and fires the sentinel's `release` event; `request()` rejects with `NotAllowedError` while hidden. So a wake lock cannot be held by a hidden page by design; it must be re-requested when visible again. This is consistent with the Health log's `wake lock lost` note.
7. WebSocket close behaviour (websockets.spec.whatwg.org, sections 3.1, 4, 5, 7; RFC 6455 7.1.5, 7.4.1):
   - If the connection ends without a Close frame (network loss, reset, TLS failure, peer vanished), the browser reports `close` with code 1006 and `wasClean` false; scripts must not be able to tell the cause apart. 1006 is reserved and never sent on the wire.
   - When a document goes away the browser starts the closing handshake with 1001; garbage collection of an open socket closes it with no status code.
   - Ping and Pong frames are not exposed to scripts. Browsers may send their own pings at discretion; the spec sets no interval. Endpoints MUST answer a ping with a pong (RFC 6455 5.5.2), so the Binance server pings are answered by the browser, not by our code, as long as the browser is running that thread.
   - Network change, laptop sleep and resume: the specs do not describe these at all; they surface as a 1006 close (or as a socket that stays "open" until a timeout). The spec is silent on sleep and resume. This is PLAUSIBLE, not stated.

## 4. Candidate explanations, ranked by documentation support

1. Binance 24-hour connection lifetime. SUPPORTED (Binance, Connect page: each connection valid 24 h). Applies to every Binance socket in the worker (derivs stream, depth, spot, trades) and the page feeds; produces a clean "closed, reopening" once per socket per day of continuous uptime. It cannot explain a shorter period.
2. Hyperliquid idle timeout of 60 s measured on server-sent messages, plus documented periodic server disconnects. SUPPORTED. Our pings are every 30 s or less, so the idle rule alone should not close a ping-answering socket, but the docs state disconnects may happen "periodically and without announcement". A period is not stated.
3. OKX 30 s no-data rule. SUPPORTED. Our ping is 20 s, so this applies only if pings are late: for example when the worker's `tick` (1 s timer, 20 s ping check) is delayed past 30 s. Late ticks in the worker are PLAUSIBLE if worker timers are throttled or the whole page is frozen (item 5).
4. Deribit: a heartbeat is never set and the docs are silent on idle timeouts without one. Closes with code 4000 are documented only for connections that DID set a heartbeat. So no Deribit close is expected from the heartbeat rule in our configuration; a Deribit close would come from our own 60 s silence rule (a quiet `deribit_volatility_index` channel: update frequency not verified, the page for that channel returned 404), from the 10028 / `connection_too_slow` rules, or from an unannounced drop. UNVERIFIED which.
5. Our own silence watchdogs closing a healthy but quiet socket (30 s for venues/books/HL/derivs 15 s) and then printing "closed, reopening" for it. Consistent with the code (worker:177, 210, 247, 342, 372, 384); it explains periodic closes if a channel really has quiet stretches, or if the worker's timestamps `s.last` stop updating while the worker is not scheduled. PLAUSIBLE, not a documented venue behaviour.
6. Worker or page scheduling delays (hidden-page intensive throttling about once a minute, freezing, Memory Saver discarding, computer sleep) producing both the per-minute `gap` notes and bursts of reconnects when scheduling resumes. The gap notes themselves are SUPPORTED as the documented Chrome 88 intensive-throttling behaviour for the page's chained 1 s timer. Whether the Worker is affected is UNVERIFIED (docs silent). Reconnects after sleep or network change are PLAUSIBLE (RFC and WHATWG say a lost connection ends with 1006; they do not mention sleep).
7. OKX port 8443 retirement. SUPPORTED that an announcement exists and that the connection stays open after the notice; no source I read says it closes connections or gives a date. Treat as a risk, not as an explanation.
8. Rate and connection limits: Binance 10 incoming messages/s per connection (we send few messages; resubscribe on book gaps sends two), Hyperliquid 30 new connections per minute per IP (reconnect storms from several tabs could approach it; one connection reopening every 5 s is 12/min per socket), OKX 3 connection requests/s per IP, Deribit 32 connections per IP. All SUPPORTED as limits; none shown to be reached. Hyperliquid's 10-user limit is at the cap by design when 10 wallets are followed.
9. Binance routed-path mismatch: a stream on the wrong path (for example `@depth` on `/market` or `@markPrice` on `/public`, or the legacy URL after its stated decommission date of 2026-04-23) would not push. The Binance changelog gives the decommission date; whether the page's "legacy" option still works today is UNVERIFIED. The worker's URLs use routed paths. This would show as silence then our own close, not as a server close.

## 5. What data would settle it

Currently recorded: `collector error` notes with the source name and the text "closed, reopening" at most once per source per 5 minutes (worker:17-20); the page-side `gap`, `silent`/`back`, `price-stream drop` (with `upMs`, `silentMs`, only for the auto-record stream), `tab visible/hidden`, `page frozen`, `page resumed`, `pagehide`, `load` with `discarded`, `wake lock lost`.

Logging that would separate the explanations (logging only, no behaviour change):
- On every worker socket close: the close `code`, `wasClean`, `reason`, time since open (`upMs`), time since the last message (`silentMs`), and a flag saying whether OUR silence check called `close()` just before (this distinguishes explanation 5 from server closes). Do not rate-limit this line per source the way `say` does; keep a counter instead.
- On every socket `error` event (currently ignored).
- For the worker: the actual interval between its 1 s ticks (max and p95 per minute) and `Date.now()` minus `performance.now()` drift, posted in the existing heartbeat note, so worker scheduling can be compared with the page's `gap` notes. This directly tests whether the Worker is slowed while its page is hidden (documentation is silent).
- Per socket: count of messages per minute and the longest inter-message gap, so quiet channels are visible (tests the 15/30/60 s thresholds).
- The wall-clock time of each close modulo 24 h since that socket's first open, to test the Binance 24 h rule; and the time of each close in relation to the page's `tab hidden`, `freeze`, `resume` and `gap` notes.
- Deribit: the first 200 characters of any non-subscription message (heartbeat or error object, if any appears), and the close code (4000 would mean a heartbeat close).
- OKX: log whether the "port 8443 will be retired" text arrives (currently a non-JSON or unparsed message is dropped silently at the `JSON.parse` catch, worker:163, 189).
